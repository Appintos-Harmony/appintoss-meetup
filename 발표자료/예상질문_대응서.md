## 2. 비동기 폴링 (실시간 아님) — Q1

**예상 공격:** "요즘 협업 앱은 다 실시간인데 1.5초 폴링이면 옛날 방식 아닌가요? 합주라면서 동시 연주가 안 되네요."

**핵심 답:**
- 하모니의 합주 모델은 **동시 연주(jam)가 아니라 비동기 레이어("얹기")**다. A가 반주를 녹음해 공유 코드를 만들면, B가 그 코드로 트랙을 받아 자기 악기를 **얹는다**. 시간 동기가 필요한 동시 연주가 아니므로 실시간 양방향 채널이 필요 없다.
- 구현은 클라이언트가 공유 세션을 **1.5초 간격으로 폴링**(`apps/miniapp/src/routes/Studio.tsx:267`, `setInterval(... , 1500)`)해 새 트랙이 들어왔는지 확인하는 방식이다. 트랙은 서버에 append-only로 쌓인다(`POST /sessions/:code/tracks`).
- 실시간 소켓(WebSocket)을 **의도적으로 범위에서 뺀** 결정이다. 근거: ① 7일 일정 안에서 구현·운영 부담을 줄임 ② 무의존 백엔드(`node:http` + `node:sqlite`) 원칙 유지 ③ 비동기 레이어에는 폴링으로 충분. 발표 스토리보드 S4·S5에 동일하게 명시돼 있다.

**역공 한 줄:** "실시간이 필요한 제품이면 폴링은 약점이지만, 하모니는 '얹기'라 실시간이 오히려 과설계입니다."

## 3. 익명키 mock 현황 — Q2

**예상 공격:** "토스 미니앱이라면서 토스 인증을 안 붙였네요. 사용자 식별은 가짜 아닌가요?"

**핵심 답:**
- 식별 정책은 이미 확정됐다 — **토스 로그인/자체 회원가입 금지 → `getAnonymousKey` 익명 식별 + 닉네임**(DL-016). 비게임 미니앱에 맞는 최소 식별이다.
- 현재 코드는 `apps/miniapp/src/lib/identity.ts`에서 **mock fallback**으로 익명키를 만든다(localStorage 기반). 같은 파일에 프로덕션 교체 지점이 주석으로 명시돼 있다: `@apps-in-toss/web-framework`의 `getAnonymousKey`로 **import 한 줄 교체**.
- 이 자리를 mock으로 둔 이유: 실제 `getAnonymousKey`는 토스 WebView 컨텍스트에서만 정상 반환되고, 브라우저 개발·시연 환경에선 undefined가 날 수 있다. 그래서 **앱 등록(ait deploy) 이후 실연동**하는 것이 순서다. 온보딩 화면도 발급 실패 시 버튼을 복구하도록 처리해 뒀다(`Onboarding.tsx:15`).

**정직 표기:** "식별 **설계와 교체 지점은 완료**, 실연동은 앱 등록 후 잔여"로 말한다. "토스 인증 붙였다"고 하지 않는다. (25점 대응표 §1 "`getAnonymousKey` 실연동"을 잔여로 명시한 것과 일치.)

## 4. 독립검토 대행의 한계 — Q3 (정직 방어, 가장 중요)

**예상 공격:** "독립검토를 다른 AI가 했다는데, 결국 같은 팀이 돌린 거 아닌가요? Codex가 진짜 했나요, Claude가 대행했나요?"

**핵심 답 (절대 과장 금지):**
- 먼저 구조를 정직하게 말한다 — 통제면 ChatGPT Pro는 **실제 별도 모델**이다. Claude Code가 작업지시·검토 프롬프트를 작성하면 사람이 ChatGPT Pro(및 Gemini Pro)에 입력해 독립 판정·4-AI 토의를 받았고(산출물 = 토론기록 DEBATE-011·013), 여기에 더해 **Claude Code ↔ Codex 이종(異種) 교차검토**는 실행 로그·REVIEW로 증명된다. 구현한 모델과 다른 계열 모델이 결함을 잡는 구조이고, 아래 사례가 그 증거다.
- 우리는 **실제 Codex 실행 로그가 있는 검토만 'Codex'로 표기**한다. 대표 증거:
  - **REVIEW-038 (No-Go) → 039 → 040 (Go)**: 공개 커뮤니티 보드(`Community.tsx`) PR을 Codex 독립검토가 No-Go로 막았다. 공개 보드에 노출된 `code`만으로 타인 세션에 트랙을 얹는 IDOR, 신고 키회전 자동숨김, XFF 위조 레이트리밋 우회를 잡아냈고, 수정·재검토를 거쳐 보안 블랙박스 **7 PASS / 0 FAIL**로 Go까지 끌어올렸다. ("AI가 만든 코드의 보안 결함을 다른 계열 AI가 잡고 사람이 승인해 고쳤다"의 핵심 사례.)
  - **REVIEW-20260620-011 (NO-GO)**: **Claude Code 구현**(TASK-010 커밋 헬퍼)의 pathspec magic 경로 우회를 **Codex 독립검토**가 NO-GO로 잡아 수정·재검토했다. 구현자와 검토자가 다른 모델이라는 점을 한 줄로 보여주는 보조 사례다.
- **로그가 없는 검토는 Codex가 한 척하지 않는다.** 그런 건 "Claude 대행 — 교차계열 독립성 한계"로 문서에 명시한다. 같은 모델이 자기 작업을 자기 승인하지 않는다는 원칙(CLAUDE.md §7.4)은 지키되, 교차계열 독립성을 100% 보장했다고는 말하지 않는다.
- 그리고 **최종 승인자는 항상 사람**이다(이상혁/곽소정/김민혁/양록빈). AI는 승인자가 아니다 — 문서 owner·reviewer·approver는 실제 사람만 기록한다.

**역공 한 줄:** "AI 검토의 한계를 아는 게 핵심입니다. 그래서 ① 다른 계열 모델로 교차검토하고 ② 로그 없는 건은 대행으로 정직히 표기하고 ③ 사람이 최종 승인합니다. '완벽한 독립성'을 주장하지 않는 게 우리 파이프라인의 정직성입니다."

근거: [25점 대응표 §3](../산출물/09_AI개발파이프라인/평가_25점_대응표.md), [평가 증빙 맵 §2](../평가증빙/평가_증빙_맵.md).

## 5. 샘플 차단 시 신스(synth) 폴백 — Q4

**예상 공격:** "악기 소리를 외부 CDN 샘플로 받네요. 발표장 네트워크가 막히거나 CDN이 죽으면 소리가 안 나는 거 아닌가요?"

**핵심 답:**
- 음원은 **2단 구조**다(`apps/miniapp/src/audio/engine.ts`). 1순위는 실제 샘플 음원(피아노=Salamander CC-BY, 기타/베이스=nbrosowsky, 드럼=Tone.js drum-samples, jsDelivr/CDN). 2순위는 **Tone.js 합성(synth) 폴백**(`makeSynthFor`, 악기별 oscillator+envelope 프리셋).
- 샘플 로딩이 실패하거나 차단되면 **합성 폴백으로 자동 전환**돼 소리는 항상 난다. 즉 음질은 떨어질 수 있어도 **연주·녹음·합주 기능 자체는 네트워크 0 상태에서도 동작**한다.
- 발표 대비: 시연 전 한 번 로딩해 샘플을 캐시에 올려두고, 만약을 대비해 합성 모드도 정상임을 리허설에서 확인한다(데모 백업: 녹화·스크린샷).

**역공 한 줄:** "네트워크가 죽어도 소리는 납니다. 샘플은 음질 향상용 보너스고, 합성 엔진이 항상 받쳐줍니다."

## 6. TDS 미사용 사유 — Q5

**예상 공격:** "비게임 미니앱은 TDS가 필수라고 들었는데, 화면을 자체 컴포넌트로 만들었네요. 심사 통과 가능한가요?"

**핵심 답 (정직하게):**
- TDS 패키지는 **이미 설치돼 있다**(`@toss/tds-mobile`, `@toss/tds-mobile-ait`, package.json). 다만 현재 화면은 **자체 컴포넌트 + 토스 디자인 토큰 기준의 theme.css**로 만들었고, TDS 컴포넌트를 직접 import해 쓰진 않았다(소스에 TDS import 없음).
- 그렇게 한 이유: 하모니의 핵심 화면은 **건반·지판·드럼 패드·코드 매트릭스·피아노롤** 같은 악기 연주 UI다. 여기엔 **TDS에 대응 컴포넌트가 없어** 직접 만들 수밖에 없었다. 대신 색(#3182F6 계열)·간격·타이포·모션은 토스 기준에 맞춰 일관성을 유지했다.
- 정직한 잔여: **설정·온보딩 같은 표준 폼 화면은 TDS 컴포넌트로 교체**하는 것이 심사 제출 전 후속 작업이다. 이건 "안 한 것"이 아니라 "남은 것"으로 말한다.

**역공 한 줄:** "악기 UI는 TDS 밖 영역이라 자체 제작이 불가피했고, 표준 화면은 TDS로 맞춰 갑니다. 디자인 토큰은 이미 토스 기준입니다."

> Assumption: "비게임=TDS 필수"는 앱인토스 정책의 일반 가이드다. 악기 연주 UI 같은 비표준 화면의 TDS 예외 범위는 심사 제출 시 공식 문서로 재확인할 항목(Open Question)으로 둔다.

## 7. 확장성·동시성 — Q6

**예상 공격:** "백엔드가 sqlite 파일 하나에 의존성 0이네요. 동시 접속이 몰리면 무너지지 않나요? 실서비스로 못 가는 장난감 아닌가요?"

**핵심 답:**
- 의존성 0(`node:http` + `node:sqlite`, Node 24)은 **7일 데모를 기한 안에 배포·유지하기 위한 의도된 결정**이다. 빌드 도구·ORM·웹프레임워크 없이 단일 프로세스로 AWS에 올렸다(systemd `harmony-api` :8080 + nginx TLS + certbot, `https://3.39.167.74.nip.io` 운영 중).
- 동시성: 합주는 **공유 코드 단위로 격리**돼 있고 트랙은 append-only(INSERT 위주)라 락 경합이 거의 없다. 읽기는 코드별 단순 조회다. 데모 규모에서 sqlite로 충분하다.
- 확장 경로: 데이터 접근을 **`server.mjs`의 좁은 쿼리 4곳으로 한정**해 뒀다. 부하가 오르면 이 접근부만 바꿔 **Postgres/RDS로 교체**할 수 있다(CLAUDE.md 기술 기준의 PostgreSQL 방향과 일치). 즉 확장은 "재설계"가 아니라 "교체"다.

**역공 한 줄:** "지금 규모엔 sqlite가 정답이고, 커지면 데이터 접근부만 갈아끼우면 됩니다. 일정 안에 진짜 배포하는 걸 우선했습니다."

## 8. 인증·권한 (접근 모델) — Q7

**예상 공격:** "API에 인증이 없네요. 코드만 알면 아무나 남의 합주를 망칠 수 있는 것 아닌가요?"

**핵심 답:**
- 데모 범위에선 **공유 코드 = 접근권한** 모델이다. 코드는 6자, 혼동 문자(0/O/1/I) 제외 32자에서 생성(`server.mjs` `genCode`)이라 추측이 쉽지 않다.
- 보호의 핵심은 **트랙이 append-only**라는 점이다. 트랙을 얹을 순 있어도 **남의 트랙을 수정·삭제하는 API가 없다**. 즉 "망치는" 동작 자체가 설계상 불가능하다.
- 저장 데이터의 민감도가 낮다: **결제·개인정보 수집·공개 프로필이 없다.** 식별은 익명키+닉네임뿐이고, 저장 데이터는 트랙(악보 이벤트)·세션 메타뿐이라 유출 시 영향이 제한적이다.
- 정직한 한계: 위험 표면이 "작다"고 단정하지 않는다. **공개 커뮤니티 보드(`Community.tsx`)를 붙이면서 익명 UGC 남용면이 생겼고**, 그 결함(공개 코드 트랙 오염 IDOR, 신고 키회전 자동숨김, XFF 위조 레이트리밋 우회)을 Codex 독립검토(REVIEW-038)가 No-Go로 잡았다. 수정 후 보안 블랙박스 **7 PASS / 0 FAIL**로 Go(REVIEW-040)가 났다. 공개 보드는 신고·숨김 기능을 갖췄고, 실서비스 전엔 서버측 식별(익명키 소유 검증)·rate limit 강화를 더 다듬는 게 후속이다.

**역공 한 줄:** "코드는 접근권한이고, 남의 트랙은 못 고칩니다. 공개 보드를 붙이며 생긴 남용면은 Codex 독립검토가 No-Go로 막고 고쳐 보안 블랙박스 7/7로 통과했습니다. 결제·개인정보가 없어 유출 민감도는 낮습니다."

## 9. 토스 WebView 미등록 (브라우저 시연) — Q8

**예상 공격:** "토스 미니앱이라면서 왜 토스 앱 안에서 안 보여주고 브라우저로 시연하나요?"

**핵심 답 (가장 정직하게):**
- 사실대로 말한다 — **토스 WebView 등록(`ait deploy`)은 아직 안 됐다.** 잔여는 앱 등록 + `granite.config.ts`의 `appName`을 `meetup-lite`(테스트 재사용 ID)에서 `harmony`로 교체 후 `ait deploy`(토스 콘솔 로그인 필요, AI 단독 실행 불가)다.
- 다만 **브라우저 시연은 가짜가 아니다.** HTTPS 배포(`https://3.39.167.74.nip.io`)가 실제 운영 중이고, 거기서 연주→녹음→공유→얹기→합주 재생이 실제로 동작한다.
- WebView 적합성 근거: **토스 WebView 카메라 작동을 실기기(S23 Ultra)에서 확인**했고(제스처 핸드트래킹), `granite.config.ts`에 카메라 권한·인라인 미디어 재생 등 WebView 설정을 이미 넣어 뒀다.

**역공 한 줄:** "WebView 등록은 사람이 토스 콘솔에서 할 마지막 한 단계입니다. 카메라 작동은 실기기로 확인했고, 지금 보시는 건 실제 배포 화면입니다."

근거: [평가 증빙 맵 §4](../평가증빙/평가_증빙_맵.md).

## 9.5 공개 커뮤니티 보드 (UGC 안전) — Q9

**예상 공격:** "합주 세션을 공개 보드(`Community.tsx`)에 올린다는데, 누구나 보는 공개 UGC면 개인정보 노출·악성 게시·도배 위험이 큰 것 아닌가요?"

**핵심 답 (정직하게):**
- **노출되는 식별 정보가 없다.** 공개 보드에 올라가는 건 세션 메타(곡 이름·악기 구성·좋아요 수)와 닉네임뿐이다. 사용자 식별은 **익명키 + 닉네임**(DL-016)이라 실명·연락처·위치 같은 민감정보를 수집·표시하지 않는다. 결제·공개 프로필도 없다.
- **신고·숨김이 제품 기능으로 들어가 있다.** 댓글은 신고 임계 도달 시 자동숨김되고(`POST .../comments/:id/report`), 주최자는 자기 세션을 보드에서 숨길 수 있다(`POST /sessions/:code/hide`). "약관 문구"가 아니라 API·화면에서 동작하는 기능이다.
- 가장 중요한 정직 포인트: **우리가 이 보드를 공개로 노출하면서 생긴 결함을, 다른 계열 AI가 막았다.** Codex 독립검토(REVIEW-038)가 공개 보드 PR을 **No-Go**로 막으며 ① 공개 `code`만으로 타인 세션에 트랙을 얹는 IDOR ② 신고 키회전 자동숨김 ③ XFF 위조 레이트리밋 우회를 짚어냈다. 수정·재검토를 거쳐 보안 블랙박스 **7 PASS / 0 FAIL**로 **Go**(REVIEW-040)가 났다. 즉 공개 보드는 "결함을 모른 채 띄운 것"이 아니라 "독립검토로 막고 고친 뒤 올린 것"이다.

**역공 한 줄:** "공개 보드라 위험이 커진 건 맞고, 그래서 신고·숨김을 넣고 Codex 독립검토로 공개 보드 결함을 No-Go로 잡아 고친 뒤 보안 블랙박스 7/7로 통과시켰습니다. 노출되는 건 닉네임과 곡 메타뿐, 민감정보는 없습니다."

근거: [통합테스트 결과서](../산출물/06_테스트/통합테스트_결과서.md) IT-API-07·10·12·IT-SEC, REVIEW-038~040.

## 정직성 원칙 (발표 전 전원 합의)

- 구현하지 않은 기능을 구현한 것처럼 말하지 않는다.
- 안 돌린 테스트를 통과로 말하지 않는다. 잔여는 "남은 것"으로, 약점은 "왜 그렇게 결정했는지"로 답한다.
- 독립검토는 실제 Codex 로그가 있을 때만 Codex로 말한다. 없으면 대행·한계로 정직히 말한다.
- ⓐ(AI 운영 파이프라인·증명됨)와 ⓑ(제품 구현·기본검증됨, 실기기·심사 잔여)를 섞지 않는다.

# 제품 요구사항 정의서 (PRD) — 하모니

> 피벗(DL-018, 소모임 밋업 → 악기 합주)으로 전면 재작성. 이전 소모임 PRD(FR-001~014, POL-001~005)는 폐기.
> FR 정본은 [서비스_기능정의서](서비스_기능정의서.md), FR↔화면↔모듈↔테스트 매핑은 [요구사항_추적표](요구사항_추적표.md). 이 문서는 문제·대상·흐름·비기능·정책·비목표를 다루고 FR은 중복하지 않고 ID로만 참조한다.
> 인증은 토스 로그인 제외·getAnonymousKey 익명키(DL-016). 풀버전 스코프는 DL-022(곽소정 원안 복귀).

## 1. 문제 / 대상 / 비목표

- 문제: 악기를 다뤄 한 곡을 합주로 완성하려면 사람·장비·합주실을 같은 시간에 모아야 한다. 혼자서는 한 번에 한 악기밖에 못 친다.
- 해결: 토스 안에서 한 명이 악기를 연주·녹음하고, 그 트랙 위에 다른 악기를 얹어 비동기로 한 곡을 쌓는다. 친구 트랙은 공유 코드로 받아 그 위에 내 레이어를 더한다.
- 대상: 악기를 조금이라도 다뤄봤거나 코드 매트릭스로 따라 칠 수 있는 토스 사용자. 별도 가입 없음.
- 비목표(MVP): 오프라인 합주실 예약·실시간 동시 합주(WebSocket)·계정/로그인/권한·공개 합주 피드·오디오 파일 업로드·운영자 화면. 합주는 공유 코드 + 1.5초 폴링으로 처리하고 실시간 세션은 만들지 않는다(DL-019).

## 2. 핵심 사용자 흐름

연주 → 녹음 → (저장/공유) → 얹기. 한 흐름이 배포 환경에서 끝까지 작동한다.

1. 익명키로 진입하고 닉네임을 1회 정한다(가입·로그인 없음).
2. 악기(피아노/기타/베이스/드럼)와 사용할 코드를 고른다.
3. 메트로놈 + 1마디 카운트인에 맞춰 코드/멜로디/드럼을 연주한다. 입력은 터치, 카메라 제스처(MediaPipe) 중 택1(동시 바인딩 금지, 카메라 실패 시 터치 폴백).
4. 녹음하면 tick 기준 이벤트로 기록되고 바로 재생된다. 피아노롤에서 빨간 재생위치선을 드래그해 음을 편집한다.
5. 트랙을 로컬에 저장하거나 공유 코드를 발급해 클립보드로 복사한다.
6. 친구가 코드/클립보드로 트랙을 받아 세션을 연다.
7. 받은 트랙을 들으며(녹음 중 기존 레이어 모니터링) 내 악기 레이어를 얹는다.
8. 세션 전체 트랙을 트랙별 음색으로 동시 재생해 합주를 확인한다. 새 레이어는 1.5초 폴링으로 반영된다.

## 6. 안전·악용

이 제품은 오프라인 활동·위치·대면 만남이 없어 소모임 밋업의 안전 규칙(금지구역·접촉·집결지 노출 등)은 해당하지 않는다. 남는 위험은 공유 채널뿐이다.

- 공유 코드: 코드를 아는 사람만 세션에 얹을 수 있다. 코드는 추측 가능성을 낮춘 값으로 발급하고, 폴링으로 받는 트랙은 신뢰하지 않는 입력으로 다룬다(서버 검증).
- 악용 시나리오: 무관한 데이터를 세션에 얹기, 공유 엔드포인트 남용. 4엔드포인트(`/healthz`·POST `/sessions`·GET `/sessions/:code`·POST `.../tracks`) 입력 검증으로 막고, 업로드 트랙은 events·instrument·style·owner 스키마로 제한한다.

## 7. 성공 지표 (측정 이벤트만, 수치 미정)

발표 시연 기준 지표: 트랙 녹음 완료 수, 공유 코드 발급 수, 코드로 받기 성공률, 얹기 후 합주 재생 도달. 실측 전 수치는 작성하지 않는다.

## 8. 시스템 메모 (PRD 범위)

- 백엔드: Node24 `node:http` + `node:sqlite`(무의존). tracks에 owner·events·instrument·style 저장. 합주 = 공유 코드 + 1.5초 폴링.
- 프론트: vite build → `/opt/harmony-web`, systemd `harmony-api`(:8080), nginx 정적 + 리버스프록시. 상세는 시스템 구성도·API 명세서·테이블 정의서.

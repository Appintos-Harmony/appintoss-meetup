# 롤백 계획서 (하모니)

> [배포_실행절차서](배포_실행절차서.md) §E의 롤백 항목을 독립 문서로 분리·확장한다. 대상은 운영 중인 백엔드(AWS Ubuntu, nginx 정적 미니앱 + systemd `harmony-api` + SQLite). 미니앱 토스 배포(`ait deploy`) 롤백은 토스 콘솔 심사 단위라 본 문서 범위 밖이며 절차서 §B를 따른다.

## A. 적용 대상과 전제

- 운영 도메인: `https://3.39.167.74.nip.io` (nginx TLS + Let's Encrypt). 한 도메인에서 정적 미니앱(`/opt/harmony-web`)과 API(`/healthz`, `/sessions`)를 함께 서빙한다. 계약: [nginx-harmony-api.conf](../../apps/api/deploy/nginx-harmony-api.conf).
- 서비스: systemd `harmony-api`(:8080) · [harmony-api.service](../../apps/api/deploy/harmony-api.service). `DB_PATH=/opt/harmony-api/data/harmony.db`.
- 실행 주체: **사람**(SSH 접속). AI는 절차 준비·점검만 한다. SSH 키(pem)는 저장소 미반영(DL-021).
- 전제: 현재 [deploy.sh](../../apps/api/deploy/deploy.sh)는 배포 시 `server.mjs`를 버전 백업 없이 덮어쓴다. 따라서 **롤백은 배포 직전에 백업을 떠 둔 경우에만 보장된다**(§E 사전 준비 참조). 백업이 없으면 Git에서 이전 커밋의 `server.mjs`를 받아 복구한다.

## B. 롤백 트리거

| 트리거 | 판단 기준 | 조치 |
|---|---|---|
| API 헬스체크 실패 | `curl https://3.39.167.74.nip.io/healthz` 가 `{ok:true}` 아님(2xx 아님) | §D 백엔드 롤백 |
| 미니앱 정적 깨짐 | 도메인 루트가 흰 화면·이전 빌드와 다른 오류 | §C 정적 롤백 |
| 공유/얹기 회귀 | `POST /sessions` 또는 `/sessions/:code/tracks` 5xx·계약 불일치(클라 `src/lib/share.ts` 깨짐) | §D 백엔드 롤백 |
| 발표 임박(D-day, 06-26) 변경 후 이상 | 발표 전 스모크에서 핵심 흐름 1건이라도 실패 | 즉시 직전 정상본으로 롤백, 변경 보류 |

발표일 14:00 기준, 변경은 충분한 검증 시간이 없으면 적용하지 않고 직전 정상본을 유지한다(CLAUDE.md §17: 06-25 이후 발표를 깨뜨릴 변경 금지).

## C. nginx 정적 미니앱 복구 (이전 dist)

정적 미니앱은 `/opt/harmony-web`에 배포된다. 이전 `dist`로 되돌린다.

```bash
# 0) 현재 본을 백업(되돌리기 전 항상)
sudo mv /opt/harmony-web /opt/harmony-web.bad-$(date +%Y%m%d-%H%M%S)

# 1) 직전 정상 dist 복구 (배포 전 보관해 둔 백업 경로 사용)
sudo cp -a /opt/harmony-web.bak-<직전배포타임스탬프> /opt/harmony-web

# 2) 권한·reload (배포 절차서와 동일 계약)
sudo chmod -R a+rX /opt/harmony-web
sudo nginx -t && sudo systemctl reload nginx
```

- 백업본이 없으면: 직전 정상 커밋에서 미니앱을 재빌드해 복구한다. `cd apps/miniapp && VITE_API_BASE=https://3.39.167.74.nip.io npm run build` → `dist`를 서버 `/opt/harmony-web`로 교체. `VITE_API_BASE` 누락 시 기본값 `http://localhost:8080`으로 빌드되어 실기기 공유가 실패하므로 반드시 주입한다(절차서 §B-2).
- nginx 설정 파일 자체 회귀 시: [nginx-harmony-api.conf](../../apps/api/deploy/nginx-harmony-api.conf)의 검증된 본을 `/etc/nginx/...`로 되돌리고 `sudo nginx -t && sudo systemctl reload nginx`.

## D. systemd harmony-api 재시작 / 이전 server.mjs

API는 무의존(`node:http` + `node:sqlite`) 단일 파일 `server.mjs`다. 코드 회귀는 이전 `server.mjs`로 교체 후 재시작한다.

```bash
# 0) 우선 단순 재시작으로 회복되는지 확인(일시 장애·메모리)
sudo systemctl restart harmony-api
sleep 1 && curl -fsS http://localhost:8080/healthz

# 1) 코드 롤백: 직전 정상 server.mjs로 교체
sudo cp /opt/harmony-api/server.mjs /opt/harmony-api/server.mjs.bad-$(date +%Y%m%d-%H%M%S)
sudo cp /opt/harmony-api/server.mjs.bak-<직전배포타임스탬프> /opt/harmony-api/server.mjs
sudo chown harmony:harmony /opt/harmony-api/server.mjs

# 2) 재시작·헬스체크
sudo systemctl restart harmony-api
sleep 1 && curl -fsS http://localhost:8080/healthz
```

- 백업본이 없으면 Git에서 이전 정상 커밋의 파일을 복구한다. 현재 형상 기준 마지막 feature 커밋은 `6372dc3`(그 위 조장 docs 커밋 `ebdad0a`, develop 푸시됨).
  - 예: `git show 6372dc3:apps/api/server.mjs > /tmp/server.mjs` → 서버 `/opt/harmony-api/server.mjs`로 교체 → 재시작.
- 서비스 유닛 파일 자체 회귀 시: [harmony-api.service](../../apps/api/deploy/harmony-api.service)를 `/etc/systemd/system/`로 되돌리고 `sudo systemctl daemon-reload && sudo systemctl restart harmony-api`.
- 스키마 호환: `server.mjs`는 기동 시 `tracks`에 `instrument`·`style` 컬럼이 없으면 추가하고 있으면 무시한다(server.mjs 13~20행). 따라서 신버전→구버전 코드 롤백 시에도 기존 DB는 그대로 사용 가능하다(컬럼은 남고 구버전은 미사용). **별도 DB 마이그레이션 다운그레이드는 불필요**하다.

## E. SQLite 백업 위치와 데이터 복구

- 운영 DB 파일: `/opt/harmony-api/data/harmony.db` (소유자 `harmony:harmony`, systemd `DB_PATH`로 고정).
- 코드 롤백은 데이터에 영향을 주지 않는다(같은 DB 파일 유지). DB 파일 자체가 손상·오염된 경우에만 아래 복구를 쓴다.

**배포 직전 사전 백업(권장 · 사람이 배포 전 실행):**
```bash
TS=$(date +%Y%m%d-%H%M%S)
# 코드·정적·DB를 같은 타임스탬프로 백업
sudo cp /opt/harmony-api/server.mjs /opt/harmony-api/server.mjs.bak-$TS
sudo cp -a /opt/harmony-web /opt/harmony-web.bak-$TS
# SQLite는 핫백업 API로 일관성 보장(단순 cp 대신 권장)
sudo -u harmony sqlite3 /opt/harmony-api/data/harmony.db ".backup '/opt/harmony-api/data/harmony.db.bak-$TS'"
```
- `sqlite3`가 없으면 서비스를 잠깐 멈추고 cp: `sudo systemctl stop harmony-api && sudo cp /opt/harmony-api/data/harmony.db /opt/harmony-api/data/harmony.db.bak-$TS && sudo systemctl start harmony-api`.

**DB 복구:**
```bash
sudo systemctl stop harmony-api
sudo cp /opt/harmony-api/data/harmony.db /opt/harmony-api/data/harmony.db.bad-$(date +%Y%m%d-%H%M%S)
sudo cp /opt/harmony-api/data/harmony.db.bak-<타임스탬프> /opt/harmony-api/data/harmony.db
sudo chown harmony:harmony /opt/harmony-api/data/harmony.db
sudo systemctl start harmony-api
```
- 데이터 영속 검증은 통합 시나리오 "재배포 후 데이터 유지"(IT 시나리오, [통합테스트_계획서](../06_테스트/통합테스트_계획서.md))와 동일 관점이다. 롤백 후에도 기존 공유 코드로 `GET /sessions/:code`가 조회되는지 확인한다.

## F. 헬스체크 절차 (롤백 후 필수)

| 순서 | 명령/행동 | 기대 결과 |
|---|---|---|
| 1 | `sudo systemctl status harmony-api` | `active (running)` |
| 2 | `curl -fsS http://localhost:8080/healthz` | `{"ok":true,"time":...}` (서버 내부) |
| 3 | `curl -fsS https://3.39.167.74.nip.io/healthz` | `{"ok":true,...}` (nginx 경유 외부) |
| 4 | 도메인 루트 브라우저 접속 | 미니앱 정상 렌더(흰 화면·콘솔 오류 없음) |
| 5 | 공유 왕복 스모크 | `POST /sessions`(코드 발급) → `GET /sessions/:code`(트랙 조회) → `POST /sessions/:code/tracks`(얹기) 200 |
| 6 | 실기기 1건 | 토스 WebView에서 공유 코드 입력→가져오기→얹기 1회 ([앱인토스_실기기검수표](../06_테스트/앱인토스_실기기검수표.md)) |

5번 공유 스모크 예시:
```bash
CODE=$(curl -fsS -X POST https://3.39.167.74.nip.io/sessions \
  -H 'content-type: application/json' \
  -d '{"name":"rollback-smoke","bpm":120,"owner":"qa","events":[]}' | tr -d '{}"' )
echo "$CODE"   # {"code":"XXXXXX"} 형태. 코드 확인
curl -fsS https://3.39.167.74.nip.io/sessions/<발급코드>   # tracks 배열 조회
```
3~5번이 모두 통과해야 롤백 완료로 본다. 실패 시 §D 0단계(단순 재시작)부터 다시 점검한다.

## G. TLS / 백업 URL (절차서 §E 연계)

- 인증서 갱신은 `certbot.timer` 자동. 수동: `sudo certbot renew`. 인증서 만료로 HTTPS 실패 시 갱신 후 `sudo systemctl reload nginx`.
- nip.io 자체 장애 시 백업 경로: cloudflared quick tunnel(`harmony-tunnel.service`, 현재 disable). `sudo systemctl enable --now harmony-tunnel` → 로그의 임시 URL을 미니앱 `.env`의 `VITE_API_BASE`에 반영·재빌드·정적 재배포. 자세한 계약은 [배포_실행절차서](배포_실행절차서.md) §E.

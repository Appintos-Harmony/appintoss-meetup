## 토론 안건 (이 6개를 **각각 확실히 결론**낼 것 · 어물쩡 합의 금지)

- **Q1. "음원"의 정의**: (a) 이벤트 JSON 유지(현행·가벼움·얹기 호환·코드4 한정) / (b) 실제 오디오 파일(WAV/MP3 · 파일 스토리지·인코딩·용량·CDN 필요, 백엔드 대공사) / (c) 하이브리드(이벤트 저장 + 클라 오디오 export). **D-4·정책·스토리지·"얹기 연결"을 모두 좌우하는 1순위 결정.**
- **Q2. 데이터·백엔드 모델**: 기존 sessions/tracks 확장(예: is_public·title 컬럼 + likes 테이블) vs 신규 posts/likes 테이블. 필요한 엔드포인트 정확히(GET /feed?sort=recent|popular, POST 공개, POST /…/like, GET /me, DELETE 내 것).
- **Q3. 실시간**: WebSocket(ws 라이브러리=**무의존 원칙 위배**, 또는 node:http upgrade 직접) vs **polling 재사용**(현행, 무의존 유지). D-4 가치 판단.
- **Q4. 정책**: 공개 UGC 게시판 + 좋아요 = 앱인토스 **소셜/커뮤니티 분류** 가능성, **신고·차단** 요건, 공개 범위(전체공개 vs 코드+선택공개). "음원이 사람-사람 만남이 아니라 연주 데이터"라는 완화 논거의 타당성.
- **Q5. 기존 기능 연결(정확히)**: 게시판 곡 → "내 스튜디오로 얹기"(기존 getSession/addTrack 재사용 가능?). 익명키=작성자+좋아요 dedup. 스튜디오 녹음→공개 동선. 공유코드 ↔ 게시물 id 관계.
- **Q6. 규칙**: 5개 제한의 정확한 의미(보유? 공개? 동시?), 인기 산정(좋아요수/재생수), 정렬 구현.

**모든 봇 공통 출력 계약:** ① 6개 안건별 결론(근거) ② **필요한 것**(화면/엔드포인트/테이블/마이그레이션) 목록 ③ **연결할 것**(기존 모듈 재사용/신규) 목록 ④ D-4 컷라인(넣을 것/뺄 것) ⑤ 가장 큰 리스크 3.

## [Claude 입장 · 라운드1, 파일 읽고 작성함]
요지: **Q1=(c) 하이브리드(사실상 이벤트JSON 유지)**, 게시판은 기존 모델 최소 확장으로 D-4에 가능. 오디오 파일·WebSocket은 컷.

- **Q1 음원 정의 → 이벤트 JSON 유지(권장).** 근거: 현재 곡은 4코드 이벤트라 데이터가 가볍고(<수KB), 클라 Tone.js로 즉시 재생되며, **"얹기"가 이벤트 기반으로 이미 동작**. 오디오 파일로 가면 녹음·인코딩·파일 스토리지·CDN·재생 + 정책(UGC 오디오) 부담이 한꺼번에 생겨 **D-4 불가**. "들어보기"는 이벤트 재생으로 충분. (원하면 발표 후 클라측 WAV export만 추가.)
- **Q2 데이터 모델 → 기존 확장.** `sessions`에 `is_public INTEGER DEFAULT 0`·`title TEXT`·`likes INTEGER DEFAULT 0` 추가, 신규 `likes(code TEXT, anon_key TEXT, created_at, PRIMARY KEY(code, anon_key))`. 엔드포인트: `GET /feed?sort=recent|popular&limit`, `POST /sessions`에 `isPublic` 플래그, `POST /sessions/:code/like`(익명키 dedup), `GET /me/sessions?owner=`(5개), `DELETE /sessions/:code`(내 것·신고용). 게시물=공개 세션 → **신규 개념 최소**.
- **Q3 실시간 → polling 재사용(권장), WebSocket 컷.** ws 라이브러리는 무의존 원칙 위배, node:http upgrade 직접 구현은 D-4 과투자. 피드 `GET /feed` 3~5s 폴링으로 "실시간감" 충분. 좋아요는 낙관적 업데이트.
- **Q4 정책 → 신고 1개 필수 + 분류 재검토.** 공개 피드는 분류 리스크를 올리지만, 공유 단위가 **연주 음원(만남/위치/채팅 아님)**이라 '소셜·만남'과는 구분 가능, 단 정책문서를 하모니 기준으로 갱신하고 **콘텐츠 신고 버튼**은 넣어야 함. 공개범위는 "공개 피드 + 비공개 코드 공유 병행".
- **Q5 연결 → 기존 재사용 최대.** 게시물=세션코드 → "얹기"는 기존 `getSession`+`addTrack` **그대로 재사용**(신규 백엔드 거의 0). 익명키=owner+좋아요키. 스튜디오 "공유"에 "게시판 공개" 옵션 추가.
- **Q6 규칙 →** 5개=익명키당 `is_public=1` 세션 ≤5(초과 차단). 인기=likes desc. 정렬 2탭.
- **컷라인:** 컷=오디오 파일 업로드·WebSocket·운영자 모더레이션 콘솔. 넣기=공개 피드(이벤트 기반)+좋아요+최신/인기 정렬+신고+기존 얹기 연결.
- **리스크 3:** ① 정책 분류(신고 없으면 심사 위험) ② 5개/좋아요 dedup의 익명키 신뢰성(기기당 1키) ③ 공개 피드에 빈/악성 데이터 → 검증·신고 필요.

## RF별 상세

### RF-001 세션 스크립트

재판정: **해소**

`node tooling/scripts/세션_시작_컨텍스트.mjs` 출력은 `브랜치: main (아직 커밋 없음)`을 표시했다. 이는 REVIEW-007에서 지적한 “git 저장소 아님” 오인을 제거한다.

### RF-002 검증 전체 모드 분리

재판정: **해소**

`검증_전체.mjs`는 기본 모드를 `하네스 기본 검증`, strict 모드를 `엄격(strict) 검증`으로 라벨링한다. 기본 모드는 산출물 누락을 보고용으로 두어 PASS하고, strict는 산출물 누락을 hard fail로 처리한다. 이는 하네스 검증과 제품/출시 검증을 구분하므로 타당하다.

### RF-003 팀문서 미기입

재판정: **해소**

무옵션 `팀공유문서_검증.mjs`가 종료코드 0으로 PASS했다. 이전 미기입 항목은 `미정 (09:05 미팅에서 기록)` 등 명시값으로 바뀌었다.

### RF-004 테스트증빙 수치

재판정: **해소**

`테스트증빙_목록.md`는 링크 검사 md·링크 수가 재현 시점에 따라 변동한다고 명시했다. 현재 재현값은 Markdown 49개·내부 링크 44개이며, 문서의 47·42는 이전 재감사 시점 수치로 이해 가능하다.

## 남은 위험

- 첫 커밋이 아직 없어 reviewed_commit 고정은 불가하다.
- helper가 `main` 커밋과 allowed_paths 위반을 자동 차단하지 않는다.
- `검증_전체 --strict`는 제품 산출물 23건 누락으로 실패한다. 하네스 기본 PASS를 제품 완료 PASS로 오해하면 안 된다.
- 실제 `커밋.mjs --message ...` 경로는 금지되어 Not Run이다. 따라서 실제 pre-commit 훅 차단 동작은 코드와 hooksPath로만 확인했다.
- `.claude/settings.json` 권한 적용은 문서 권장안만 있고 실제 적용 여부는 Not Available이다.

## 사람 승인 질문

- 이상혁은 커밋 helper가 `main`에서 경고만 하는 정책을 승인할지, feature 브랜치 강제 차단을 요구할지 결정해야 한다.
- `git add -A` 전체 스테이징 방식을 허용할지, TASK allowed_paths 기반 스테이징으로 제한할지 결정해야 한다.
- 첫 커밋을 언제, 어떤 브랜치에서, 어떤 conventional 메시지로 실행할지 승인해야 한다.
- settings.json 권장 권한(`git add/commit allow`, `git push ask`)을 실제 적용할지 결정해야 한다.

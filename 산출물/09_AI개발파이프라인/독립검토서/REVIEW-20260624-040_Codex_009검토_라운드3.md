# TASK-009 보안 수정 라운드3 독립 재확인

## 판정

**Go.**

라운드2(REVIEW-039)의 단일 조건이었던 “`TRUST_PROXY=1` 상태에서 앱이 외부 인터페이스에 직접 바인드되면 `X-Real-IP` 위조가 가능하다”는 조건은 commit `43b124d`의 기본 `127.0.0.1` 바인드로 닫혔다. 대상 `fix/TASK-20260623-009-security` / `e04de50`에서 기본 서버는 `127.0.0.1`만 LISTEN했고, `0.0.0.0`/`::1`에는 열리지 않았다.

회귀도 통과했다. 보안 블랙박스는 신선 temp DB로 **7 PASS / 0 FAIL**, miniapp vitest는 **58/58**, build도 exit 0이다.

운영 박스 SSH 내부 확인(`ss -ltnp`, `systemctl`)은 publickey 권한이 없어 직접 수행하지 못했다. 대신 공개 표면에서 `https://3.39.167.74.nip.io/healthz`는 정상 응답했고, `http://3.39.167.74.nip.io:8080/healthz`는 timeout으로 외부 직접 접근이 차단되어 있음을 확인했다. 배포 파일 기준으로도 `HOST=0.0.0.0` 설정은 없고, nginx는 `127.0.0.1:8080`으로만 proxy_pass하며 X-Real-IP/XFF를 `$remote_addr`로 덮어쓴다.

## §3 배포 전제 확인

| 전제 | 독립 확인 | 판정 |
|---|---|---|
| production service는 HOST 미설정 | `harmony-api.service`에 `Environment=HOST=` 없음, `Environment=TRUST_PROXY=1` 있음 | PASS |

## 잔여와 운영 주의

1. 같은 호스트 로컬 프로세스는 여전히 `TRUST_PROXY=1` 서버에 직접 `X-Real-IP`를 보낼 수 있다. 이번 수정은 원격 외부 TCP 경로를 닫는 방어이며, 루프백 자체가 신원 경계는 아니다.
2. `HOST=0.0.0.0`을 명시하면 의도대로 다시 외부 바인드가 열린다. 배포 환경에 `HOST=0.0.0.0` override를 넣지 않는 것이 필수다.
3. `harmony-tunnel.service`는 백업용 파일이 존재한다. 이 터널을 켤 경우 nginx를 우회한 2차 프록시 경로가 생길 수 있으므로, enable 전 X-Real-IP/XFF 덮어쓰기 정책을 별도로 검토해야 한다.
4. 배포 후 서버 내부에서 `ss -ltnp | grep 8080`이 `127.0.0.1:8080`만 보이는지 런북 확인을 권장한다. Codex 환경에서는 SSH publickey가 없어 내부 명령을 직접 확인하지 못했다.

## 결론

`43b124d`는 REVIEW-039의 단일 조건을 코드와 로컬 런타임에서 닫았다. 현재 공개 표면에서도 `:8080` 직접 접근은 차단되어 있어 원격 `X-Real-IP` 위조 경로가 재현되지 않는다. 기존 009 보안 블랙박스와 miniapp 회귀도 통과했으므로 라운드3 판정은 **Go**다.

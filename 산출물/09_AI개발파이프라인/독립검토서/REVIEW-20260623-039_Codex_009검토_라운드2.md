# TASK-009 커뮤니티 공유 보안 수정 라운드2 독립 재검증

## 판정

**Conditional Go.**

커밋 `72cdfbf`의 코드 수정은 REVIEW-038에서 실증한 P0/MED 재현 케이스를 닫았다. 공식 블랙박스는 포트 간섭 제거 후 **7 PASS / 0 FAIL**, 추가 직접 프로브는 **13 PASS / 0 FAIL**, miniapp 테스트와 빌드는 모두 종료코드 0으로 통과했다.

단, 배포 조건이 하나 남는다. `apps/api/deploy/harmony-api.service`는 `TRUST_PROXY=1`을 켜지만 `server.mjs`는 `server.listen(PORT)`로 모든 인터페이스에 바인드한다. nginx는 헤더를 덮어써서 안전하지만, **8080이 외부에 직접 노출되면 공격자가 `X-Real-IP`를 직접 지정해 rate/report IP 경계를 우회할 수 있다.** 레포 안에서는 보안그룹/방화벽으로 8080 직접 접근이 차단된다는 증거가 없다. 출시 전 `127.0.0.1` 바인드 또는 인프라 방화벽 증빙이 필요하다.

## C. XFF / nginx / systemd 정합성

| 항목 | 확인 결과 | 판정 |
|---|---|---|
| 앱 기본 동작 | `TRUST_PROXY` 미설정이면 XFF/X-Real-IP 무시, socket remoteAddress 사용 | PASS |
| nginx | `X-Real-IP`와 `X-Forwarded-For`를 `$remote_addr`로 덮어씀 | PASS |
| systemd | `TRUST_PROXY=1` 설정 | PASS with condition |
| 직접 노출 전제 | Node가 host 제한 없이 `server.listen(PORT)` 사용. 8080 외부 차단 증빙 없음 | 조건부 위험 |

출시 조건 제안:

```diff
- server.listen(PORT, () => console.log(`harmony-api listening on :${PORT}`));
+ const HOST = process.env.HOST || '127.0.0.1';
+ server.listen(PORT, HOST, () => console.log(`harmony-api listening on ${HOST}:${PORT}`));
```

또는 AWS 보안그룹/ufw에서 8080 외부 인바운드 차단 증빙을 배포 체크리스트에 포함해야 한다.

## D. 새 우회 시도

| 시도 | 기대 | 실제 | 판정 |
|---|---|---|---|
| hidden 세션 다른 mutation | GET/comment/like/track 모두 404 | 모두 404 | PASS |
| XFF IPv4/IPv6 변형 | `::1`, `127.0.0.1`, `::ffff:127.0.0.1` 헤더로 같은 IP 신고 우회 불가 | visible=1 | PASS |
| no-author idempotency IP fallback | 같은 IP+같은 token은 같은 code 반환 | 같은 code, `idempotent:true` | 잔여 Low |
| Content-Length 0 + 실제 body | 세션 생성 없이 오류 | `HTTP/1.1 400 Bad Request` | PASS |

`no-author` idempotency는 인증 없는 환경의 IP fallback 특성상 같은 NAT/프록시 뒤에서 동일 token이면 충돌한다. 클라이언트 token이 충분히 랜덤이면 현실 가능성은 낮지만, 장기적으로는 서버 발급 세션/nonce가 더 안전하다.

## 남은 위험

1. **배포 전제:** 8080 직접 노출 차단이 필수다. 현재 레포 파일만으로는 차단을 증명할 수 없다.
2. **약한 소유권 모델:** `author_key`가 클라이언트 보관 비밀인 한 탈취/로그 노출 시 공개 세션 owner mutation은 가능하다. 이번 수정은 공개 `code`만으로 변조되는 P0를 닫은 수준이다.
3. **신고 자동숨김:** 동일 IP 키 회전은 닫혔지만, 분산 IP 신고는 여전히 자동숨김을 유발한다. 공개 UGC 운영 전에는 신고 큐/복구/감사 로그가 필요하다.
4. **의존성 취약점:** `npm audit` 취약점 수는 이번 수정으로 새로 생긴 것은 아니지만 공개 출시 전 별도 triage가 필요하다.

## 결론

코드 레벨 방어와 정상 플로우는 라운드2 기준 통과했다. 단, 배포에서 8080 직접 접근이 차단된다는 조건을 확인하거나 `HOST=127.0.0.1` 바인드를 코드/서비스에 반영하기 전까지는 **Conditional Go**로 둔다.

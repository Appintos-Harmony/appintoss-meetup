# 유지보수 백로그

## 1. 개요

멀티에이전트(Claude Code 주 구현, Codex 독립 검증) 유지보수성 전수 감사 결과 하모니 미니앱의 종합 점수는 **73/100**이다. 세부: miniapp 뷰 62 · 도메인 82 · api 68 · tooling 74 · 횡단 76.

- **기반 강점:** TypeScript strict mode · 명시적 `:any` 0건 · 도메인 로직이 순수 함수로 분리됨(`apps/miniapp/src/audio/*`) · 단위/통합 58개 테스트 보유.
- **점수 하락 원인:** 기능 결함이 아니라 **구조 부채**다. 단일 거대 컴포넌트(`Studio.tsx`), 코드 인터벌/보이싱 정의가 3곳에 중복(진실원 3중화), API 서버의 라우트 if-체인과 catch-all 400, 공유 contract 미분리, tooling 헬퍼 중복이 주요 항목이다.

이 백로그는 §17 일정 동결(6/22 이후 핵심 기능 추가 금지, 6/24 이후 구조 변경 금지)을 준수해, **발표(6/26)에 영향 없는 항목만 즉시 적용(SAFE_NOW)** 하고, **데모 경로·응답 표면에 영향 가능한 항목은 발표 후 백로그(DEFER)** 로 분리한 결과다.

`file:line`은 develop tip(c13b818, SAFE 10건 머지 후) 기준 grep으로 재확인했다.

## 4. 권장 적용 순서

발표 후 백로그 처리 우선순위:

**DF-1 > DF-2 > DF-4 > DF-3 > DF-5**

(DF-6은 우선순위 체인 밖 · 조장 OQ 승인이 선행 조건이며 effort S·위험 0이므로 승인 즉시 별도 처리 가능.)

순서 근거: DF-1(거대 컴포넌트)은 이후 모든 miniapp 변경의 마찰을 줄이므로 선행. DF-2(음정 진실원 통합)는 도메인 정확성 직결로 차순위. DF-4(공유 contract)는 클라·서버 동기화 기반을 만들어 DF-3 서버 리팩터의 안전망이 되므로 DF-3보다 앞. DF-5(tooling 공통화)는 게이트 안정화로 마지막.

## 5. 원칙 (적용 게이트)

- **DF-2(음정 산출 경로) 발표 전 금지.** `engine.ts`의 `voiceFreqs`/`parseChord` 변경은 데모 음원 회귀에 직결된다. 발표(6/26) 종료 후에만 착수한다.
- **DF-3(백엔드 응답 코드) 발표 전 금지.** 4xx/5xx 분류 변경은 통합테스트·배포 재검증을 요구한다. §17 동결 기간에 응답 표면을 바꾸지 않는다.
- **DF-6(likes.ts 제거)은 조장(이상혁) OQ 승인 후에만.** 종료보고서·프로그램목록·기능명세서가 '보존(dead)'으로 명시했으므로, 제거 시 동일 변경에서 세 문서의 보존 기록을 함께 갱신한다.
- 모든 DEFER 항목은 §17(6/24 이후 구조 변경 금지) 동결 해제, 즉 발표 후 시점에 작업지시서(TASK) + 독립 검토(REVIEW) + 사람 승인을 거쳐 진행한다.

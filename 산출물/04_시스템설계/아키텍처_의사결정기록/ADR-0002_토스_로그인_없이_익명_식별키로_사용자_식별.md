# ADR-0002 — 토스 로그인 없이 익명 식별키로 사용자 식별

## 상태

Accepted. 근거: [DL-016](../../00_프로젝트관리/의사결정_기록.md#dl-016--토스-로그인-제외--익명-식별키getanonymouskey-채택--사업자-미등록)(이상혁 "그렇게 하자").

## 맥락

학교 프로젝트라 사업자 등록(비용·서류) 부담이 크다. 공식 문서 확인 결과:

- 미니앱 로그인은 **토스 로그인만** 허용되며 자사·소셜·간편 로그인은 불가하다([공식문서 근거 #2](../../02_정책준수/공식문서_근거목록.md)).
- **비사업자는 토스 로그인을 쓸 수 없다**([공식문서 근거 #3](../../02_정책준수/공식문서_근거목록.md)).
- 비게임 전용 익명 식별키 `getAnonymousKey`는 토스 로그인·서버 연동·사업자 없이 미니앱별 고유 hash를 제공한다.
  다만 클라이언트 식별용이며 서버 인증 토큰이 아니다([공식문서 근거 #4](../../02_정책준수/공식문서_근거목록.md)).

## 결정

1. 토스 로그인을 사용하지 않는다.
2. 사용자 식별은 `getAnonymousKey`(익명 hash)로 한다.
3. "가입" 경험은 hash 기반 닉네임 온보딩 1회로 구현한다.
4. 사업자 미등록 상태를 유지한다.
5. 익명키는 클라이언트 식별용이므로, 서버 측 약한 소유권은 클라이언트 자기신고 `author_key` + 코드 접근으로 구현하되
   레이트리밋·신고 임계 등 남용 방지는 클라이언트 키가 아니라 **서버가 도출한 IP**로 버킷팅한다(ADR-0005, 키 회전 우회 차단).

## 결과

- `apps/api/server.mjs`는 인증 없이 `code`=접근권한, `author_key`=클라이언트 자기신고 약한 소유권으로 동작한다(server.mjs 주석 5행).
- 신고/레이트리밋은 클라이언트 키가 아니라 서버 IP로 버킷팅한다(server.mjs 50~53행, 104행) — 키 회전으로 distinct 신고자 위조 불가.
- PRD 영향: FR-001(토스 로그인→익명 식별키), FR-002(닉네임 온보딩), POL(사업자 불필요)(DL-016).

### 한계 / Open Question

- **익명키 2트랙(코드 반영 완료):** 클라이언트 `getUserKey()`는 `isToss()` 분기로 토스에서 `getAnonymousKey`를 실호출하고, 일반 브라우저에서는 암호학적 난수 익명키로 폴백한다(머지 f506717).
  공식 문서상 샌드박스=호스트 제공 hash, 실기기=QR 진입이다([공식문서 근거 #4](../../02_정책준수/공식문서_근거목록.md)).
  정식 per-user 식별 검증은 정식 출시·실기기 QR 진입에서 수행한다(앱 등록·`appName=harmony` 교체는 완료).
- 익명키는 실명 신원이 아니므로 실명 검증이 필요한 기능은 범위 밖이다(DL-016).
- 공유 IP(프록시 뒤) 환경에서는 서로 다른 사용자가 한 레이트/신고 버킷으로 묶일 수 있다(server.mjs 52행, 정책 판정 대상).

## 대안

- **(a) 토스 로그인 사용:** 사업자 등록이 전제라 학교 프로젝트 일정·비용상 채택 불가(공식 근거 #2·#3).
- **(b) 자체 계정/소셜 로그인:** 정책상 미니앱 로그인은 토스 로그인만 허용되어 불가(공식 근거 #2).
- **(c) 무식별(완전 익명):** 닉네임·약한 소유권조차 없으면 합주 트랙·댓글 소유 구분이 불가 → 익명키 + 자기신고 키로 절충.

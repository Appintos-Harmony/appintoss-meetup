# 커뮤니티 + 음원 게시판 — 화면 명세서 (스캐폴드/범위 외)

> 상태: **스캐폴드/범위 외.** 2026-06-22 2차 회의 "커뮤니티 GO"로 이 명세를 시작했으나, 같은 날 DL-022(곽소정 원안 풀버전 복귀, 조장 결정)로 D-4 우선순위가 스튜디오 풀버전으로 옮겨갔다. 본 게시판(SCR-C01~C04)은 아직 구현하지 않았고, 코드에는 진입 스캐폴드만 있다(`apps/miniapp/src/routes/Community.tsx` — 데모 목록·들어보기·가져오기(fork)만, 본체는 이상혁 담당 예정). 발표 범위에 들어가면 이 문서를 설계 기준으로 다시 연다.
> 공유 단위는 **연주 이벤트(NoteEvent JSON)**다. 오디오 파일이 아니다. 와이어·저장 형식은 하위호환을 위해 `ChordEvent`(`{tick, phase, chord, source}`) 모양 그대로 두고, `NoteEvent`(코드/멜로디/드럼 판별유니온)는 그 위에 `kind`를 입힌 타입 뷰다(`apps/api/server.mjs`·`apps/miniapp/src/lib/share.ts`·`apps/miniapp/src/audio/events.ts`의 `normalizeEvents`). "음원" 정의는 미해소(아래 §5).

## 0. 배경 · 기존 기능과의 연결
- 기존: 코드 기반 비공개 합주 — `sessions(code)`/`tracks(events)`, 클라 `share.ts`(createSession/getSession/addTrack), 1.5s polling, 실패 시 프리로드 폴백.
- 게시판 = 이 모델을 공개 목록으로 확장한다.
- 연결점(반드시 정의):
  - 스튜디오 녹음 → 게시판 공개(신규 공개 플래그/엔드포인트).
  - 게시판 곡 → 받기·얹기(기존 `getSession`/`addTrack` 재사용 — 신규 최소화).
  - 익명키(getAnonymousKey) = 작성자(owner) + 좋아요 주체(중복 방지 키).

## 1. 화면 목록 (SCR-C##)
| ID | 화면 | 한 줄 |
|---|---|---|
| SCR-C01 | 커뮤니티 피드 | 공개 음원 목록 + 정렬(최신/인기) |
| SCR-C02 | 음원 상세·듣기 | 재생 · 좋아요 · 받기/얹기 진입 |
| SCR-C03 | 공개하기(업로드) | 내 곡을 게시판에 공개 |
| SCR-C04 | 내 음원 | 보유 5개 관리(공개/삭제) |

> 현 구현: 위 4화면 중 어느 것도 구현하지 않았다. `Community.tsx`는 SCR-ST-06(스튜디오에서 진입하는 데모 목록) 스캐폴드이며, 데모 곡 미리듣기와 fork(트랙을 스튜디오로 복사해 얹기 준비)까지만 동작한다.

## 2. 화면별 명세
### SCR-C01 커뮤니티 피드
- 목적: 공개된 음원을 탐색·정렬·진입.
- 요소: 정렬 탭 [최신 | 인기], 곡 카드(제목·작성자 닉·길이(초/마디)·❤️수·▶듣기), limit/무한스크롤.
- 상태: 정상 / 로딩 / 빈("첫 곡을 올려보세요") / 오류(재시도) / 실시간 갱신(신곡·좋아요수).
- 연결: 카드 탭 → C02.
### SCR-C02 음원 상세·듣기
- 목적: 재생 + 반응 + 내 스튜디오로 가져오기.
- 요소: 재생/정지, 트랙 구성(작성자·음색), ❤️좋아요(토글·중복방지), "내 스튜디오로 얹기"(기존 받기/오버더빙 재사용), 신고(⋯).
- 상태: 정상 / 로딩 / 재생오류 / 이미 좋아요.
- 연결: 얹기 → 스튜디오(기존 `addTrack` 플로우).
### SCR-C03 공개하기(업로드)
- 목적: 스튜디오에서 만든 곡을 게시판에 공개.
- 요소: 제목 입력, (음색·길이 미리보기), 공개 버튼. 5개 초과 시 차단/교체 안내.
- 상태: 작성중 / 업로드중 / 실패 / 5개 초과.
- 연결: 스튜디오 "공유" → 여기, 성공 → C01/C04.
### SCR-C04 내 음원
- 목적: 내가 공개한 음원(최대 5) 관리.
- 요소: 내 곡 리스트(좋아요수), 공개취소/삭제, 5/5 표시.
- 상태: 빈 / 5개 도달.

## 3. 데이터 · 규칙
- 정렬: 최신(created_at desc) / 인기(좋아요수 desc).
- 5개 제한: 익명키당 공개 음원 ≤ 5(초과 시 차단 또는 최古 교체 — 미해소).
- 좋아요: 익명키 기준 1회(중복 방지).
- 인기 산정: 좋아요수(재생수 포함 여부 미해소).

## 4. 정책 체크 (UGC/소셜)
- 공개 UGC 게시판이면 앱인토스 소셜/커뮤니티 분류에 걸릴 수 있어 분류 재검토가 필요하다. 현 정책문서는 "코드 기반 비공개·불특정 연결 없음"(POL-03) 기준이다.
- 신고 최소 1개(콘텐츠 신고) 권장. 차단/모더레이션 범위는 미해소.
- 완화 논거: 공유 단위가 사람-사람 만남이 아니라 연주 음원이고, 불특정 인물 매칭·위치·채팅이 없다.

## 5. 미해소 핵심 쟁점
2026-06-22 회의에서 커뮤니티+음원게시판을 정밀 합의하려고 4-AI 토론(DEBATE-20260622-012)을 준비했다. 프롬프트 팩은 [토론_프롬프트팩_커뮤니티_음원게시판.md](../09_AI개발파이프라인/토론_프롬프트팩_커뮤니티_음원게시판.md)에 있으나 토론은 진행·기록되지 않았다(`토론기록/DEBATE-20260622-012_…`·예정 DL 모두 미생성). 같은 날 DL-022로 곽소정 원안 풀버전 복귀가 결정되면서 커뮤니티 게시판은 D-4 범위에서 빠졌고, 별도 토론은 불필요해졌다. 따라서 DEBATE-20260622-012는 결번이며, 이 영역의 방향은 DL-022가 대체한다. 아래 쟁점은 게시판을 다시 범위에 넣을 때 결정한다.

1. "음원" 정의 — 이벤트 JSON(현행) / 오디오 파일 / 하이브리드?
2. 데이터·엔드포인트 모델 — 기존 sessions·tracks 확장 vs 신규 테이블(posts·likes).
3. 실시간 — WebSocket vs polling(현행 1.5s).
4. 정책 — 분류·신고·공개범위.
5. 연결 — 기존 합주(얹기)·식별(익명키)·스튜디오 공개 동선.
6. 규칙 — 5개 제한·인기 산정·정렬.

라운드1에서 정리한 Claude 입장(이벤트 JSON 유지·기존 모델 확장·polling 재사용·신고 1개·기존 얹기 재사용)은 프롬프트 팩에 남아 있다. 재개 시 출발점으로 쓴다.
